01

Cómo arranca la aplicación

Todo empieza en server.js. Cuando ejecutas npm start, ese archivo se lee de arriba a abajo una vez, y el orden importa: cada línea deja algo listo para la siguiente.

Los tres pasos numerados solo se ejecutan una vez, al arrancar el proceso. Los tres routers, en cambio, se consultan en cada petición. Por eso el orden de estas dos líneas en server.js es el que decide qué controla qué:

server.js
require("dotenv").config();          // 1. primero: llena process.env
require("./database/db");            // 2. usa esas variables para conectar
// ... configurar Express, vistas, middlewares ...
app.use("/", seoRoutes);
app.use("/", postsRoutes);
app.use("/admin", adminRoutes);
app.listen(PUERTO, ...);

Si invirtieras las dos primeras líneas, database/db.js leería process.env.ADMIN_PASSWORD antes de que dotenv lo hubiera cargado desde tu .env — y usaría el valor por defecto sin que te dieras cuenta. Es la típica trampa de orden de carga en Node.

02

Estructura de carpetas

Cada carpeta tiene una única responsabilidad. Ningún archivo de routes/ sabe cómo se dibuja una página, y ningún archivo de views/ sabe cómo se consulta la base de datos — se comunican solo a través de los datos que res.render() les pasa.

blog-web/ ├── server.js arranque, middlewares, conecta los routers ├── database/ │ ├── db.js conexión SQLite + creación de tablas │ └── blog.db el archivo de datos (no se sube a git) ├── routes/ │ ├── posts.js portada, detalle de post, comentarios │ ├── admin.js login, CRUD, imágenes, moderación │ └── seo.js robots.txt y sitemap.xml ├── views/ plantillas EJS — el HTML con huecos │ ├── partials/ header.ejs y footer.ejs, compartidos │ ├── admin/ vistas del panel │ ├── index.ejs │ └── post.ejs └── public/ ├── css/style.css servido tal cual, sin procesar └── uploads/ imágenes subidas (o el volumen en prod)

El patrón que se repite en todo el proyecto es ruta → consulta → vista: una función en routes/ recibe la petición, pide datos a database/db.js con SQL, y se los entrega a un archivo de views/ para que los convierta en HTML. Ninguna consulta SQL vive dentro de un archivo .ejs.

03

Las vistas (EJS)

EJS es HTML normal con trocitos de JavaScript metidos entre <% %>. No hay componentes ni estado: cada vista es una función que recibe un objeto de datos y devuelve texto.

Las tres formas de escribir en una plantilla
SintaxisQué haceCuándo usarla
<%= valor %>Imprime escapando HTMLCasi siempre — texto de usuarios, títulos, nombres
<%- valor %>Imprime sin escapar, HTML crudoSolo contenido que ya confías (el artículo del admin)
<% ... %>Ejecuta JS sin imprimir nadaif, forEach, variables intermedias

Esa diferencia entre <%= y <%- no es un detalle de estilo — es la barrera contra XSS de toda la app. El contenido de un artículo (que escribe el admin) se imprime con <%- post.contenido %> porque ahí sí quieres que <h2> o <strong> se rendericen. Un comentario de un lector, en cambio, se imprime con <%= comentario.contenido %>: si alguien escribe <script>...</script> en el formulario público, aparece como texto plano en pantalla, no se ejecuta.

Dos plantillas comparten cabecera y pie

views/partials/header.ejs abre el <html>, mete las etiquetas SEO/Open Graph y dibuja la barra de navegación; footer.ejs lo cierra. Toda vista empieza con un include:

views/post.ejs
<%- include('partials/header', {
  metaTitulo: post.titulo + " — Blog Dev",
  metaDescripcion: resumenLimpio,
  metaCanonica: "/post/" + post.id,
}) %>
<!-- ... el resto de la página ... -->
<%- include('partials/footer') %>

El objeto que le pasas al include es opcional variable por variable: header.ejs comprueba con typeof metaTitulo !== "undefined" y, si no te molestaste en pasarlo, usa un valor por defecto (los de la portada). Así ninguna vista está obligada a repetir las seis variables de SEO si no le importan.

Dos variables viven en todas las plantillas sin que nadie las pase

En server.js, dos middlewares corren antes que cualquier ruta y escriben en res.locals — un objeto que Express inyecta automáticamente en cada res.render() posterior, sin que la ruta tenga que acordarse de incluirlo:

server.js
app.use((req, res, next) => {
  res.locals.sesionIniciada = !!req.session.usuarioId;
  next();
});
app.use((req, res, next) => {
  res.locals.urlBase = `${req.protocol}://${req.get("host")}`;
  next();
});

sesionIniciada es lo que decide si header.ejs muestra el enlace "Panel admin" o nada. urlBase es el dominio completo (funciona igual en localhost:3000 que en Railway) — sin él, las URLs canónicas y las de Open Graph tendrían que llevar el dominio escrito a mano en el código.

04

La base de datos

database/db.js usa node:sqlite, el módulo de SQLite incluido en Node desde la versión 22.13 — sin instalar nada ni compilar nada nativo. Al hacer require("./database/db") desde server.js, este archivo se ejecuta una vez y deja la base de datos lista.

Migraciones a mano, sin librería

Las cuatro tablas se crean con CREATE TABLE IF NOT EXISTS, así que ejecutar db.js mil veces no rompe nada. El problema es cuando cambias una tabla que ya existía: categoria_id se añadió a posts después de la primera versión del blog, y no puedes meterla en el CREATE TABLE original porque ese bloque solo corre la primera vez. La solución, sin usar ninguna librería de migraciones:

database/db.js
const columnas = db.prepare("PRAGMA table_info(posts)").all();
const tieneCategoriaId = columnas.some(c => c.name === "categoria_id");
if (!tieneCategoriaId) {
  db.exec("ALTER TABLE posts ADD COLUMN categoria_id INTEGER");
}

Pregunta a SQLite qué columnas tiene la tabla ahora mismo, y si falta la nueva, la añade. Es el mismo patrón que tendrías que seguir si mañana quieres añadir, por ejemplo, un email opcional a comentarios.

El usuario admin se sincroniza en cada arranque

No hay un formulario de registro — el único usuario se crea (o se actualiza) leyendo ADMIN_EMAIL / ADMIN_PASSWORD cada vez que arranca el servidor: si no existe, lo crea; si ya existe, le sobrescribe la contraseña con un nuevo hash de bcrypt. Por eso cambiar ADMIN_PASSWORD en Railway y redesplegar es suficiente para cambiar la contraseña, sin tocar la base de datos a mano.

05

Rutas públicas

routes/posts.js — nadie necesita haber iniciado sesión para llegar aquí.

GET/portada, con filtro de categoría y buscador
GET/post/:iddetalle de un artículo
POST/post/:id/comentariospublicar un comentario

La portada construye el SQL a pedazos según lo que venga en la URL — así una sola consulta cubre "todo", "solo esta categoría", "buscar esta palabra" y "ambas cosas a la vez", sin cuatro funciones distintas:

routes/posts.js
let sql = `SELECT posts.*, categorias.nombre AS categoria_nombre
           FROM posts LEFT JOIN categorias ON posts.categoria_id = categorias.id`;
const condiciones = [];
const parametros = [];

if (categoriaId) { condiciones.push("posts.categoria_id = ?"); parametros.push(categoriaId); }
if (busqueda)    { condiciones.push("(titulo LIKE ? OR resumen LIKE ? OR contenido LIKE ?)");
                    parametros.push(`%${busqueda}%`, `%${busqueda}%`, `%${busqueda}%`); }

if (condiciones.length) sql += " WHERE " + condiciones.join(" AND ");
const posts = db.prepare(sql).all(...parametros);
Por qué son placeholders (?) y no texto pegado Los valores nunca se concatenan directamente al SQL — se pasan como parámetros separados a .all(...). Es lo que impide la inyección SQL: si alguien busca "; DROP TABLE posts; --, SQLite lo trata como un texto literal a buscar, nunca como código.

El formulario de comentarios no exige sesión iniciada — cualquier lector puede publicar. La validación es deliberadamente simple: recorta a 80/2000 caracteres y rechaza vacíos, sin librerías externas:

routes/posts.js
const nombre = (req.body.nombre || "").trim().slice(0, 80);
const contenido = (req.body.contenido || "").trim().slice(0, 2000);
if (!nombre || !contenido) {
  // vuelve a renderizar la misma página con errorComentario
}
06

Login y sesión

No hay JWT ni tokens — express-session guarda una cookie firmada en el navegador que solo contiene un id de sesión; los datos reales (usuarioId) viven en el servidor, en memoria.

routes/admin.js
router.post("/login", (req, res) => {
  const usuario = db.prepare("SELECT * FROM usuarios WHERE email = ?").get(req.body.email);
  if (!usuario || !bcrypt.compareSync(req.body.password, usuario.password)) {
    return res.render("admin/login", { error: "Email o contraseña incorrectos" });
  }
  req.session.usuarioId = usuario.id;   // esto es TODO lo que "iniciar sesión" hace
  res.redirect("/admin/dashboard");
});

La contraseña nunca se guarda ni se compara en texto plano: bcrypt.compareSync vuelve a aplicar el mismo algoritmo de hash a lo que escribiste y compara los dos hashes, no las contraseñas. Cada ruta protegida pasa por un guardia minúsculo antes de ejecutarse:

routes/admin.js
function requiereLogin(req, res, next) {
  if (!req.session.usuarioId) return res.redirect("/admin/login");
  next();
}
router.get("/dashboard", requiereLogin, (req, res) => { ... });

requiereLogin se repite como segundo argumento en cada ruta del panel — Express llama a los middlewares en el orden en que aparecen, así que si no hay sesión, la petición nunca llega a la función que borra o crea un post.

07

Panel de administración

Todo detrás de /admin exige requiereLogin, salvo el propio formulario de login.

GET/admin/dashboardlistado de artículos
GET/admin/posts/nuevoformulario en blanco
POST/admin/posts/nuevocrea el artículo
GET/admin/posts/:id/editarformulario relleno
POST/admin/posts/:id/editaractualiza
POST/admin/posts/:id/borrarborra el post, sus comentarios y su imagen
GET/admin/categoriaslistado + alta
POST/admin/categorias/:id/borrarborra; sus posts quedan sin categoría

Un mismo formulario EJS (admin/form.ejs) sirve para crear y editar: la vista recibe post como null o como el registro existente, y decide el título del botón y la acción del <form> con un ternario. Evita mantener dos plantillas casi idénticas.

Al borrar categorías y posts, el código elige explícitamente qué pasa con lo relacionado — SQLite no lo hace solo:

  • Borrar una categoría pone categoria_id = NULL en sus posts antes de borrarla — no se los lleva por delante.
  • Borrar un post sí borra en cascada sus comentarios y su archivo de imagen — no tendría sentido dejarlos huérfanos.
08

Subida de imágenes

multer intercepta el formulario (que debe llevar enctype="multipart/form-data"), separa el archivo de los demás campos de texto y lo escribe a disco antes de que tu código de ruta se ejecute.

routes/admin.js
const almacenamiento = multer.diskStorage({
  destination: (req, file, cb) => cb(null, req.app.get("carpetaUploads")),
  filename: (req, file, cb) => {
    const sufijo = `${Date.now()}-${Math.round(Math.random() * 1e9)}`;
    cb(null, `${sufijo}${path.extname(file.originalname).toLowerCase()}`);
  },
});
const subirImagen = multer({
  storage: almacenamiento,
  limits: { fileSize: 5 * 1024 * 1024 },
  fileFilter: (req, file, cb) => {
    if (!tiposPermitidos.has(file.mimetype)) return cb(new Error("TIPO_NO_PERMITIDO"));
    cb(null, true);
  },
}).single("imagen");

El nombre de archivo nunca es el que subió el usuario — es una marca de tiempo más un número aleatorio, para que dos personas subiendo portada.jpg el mismo día no se pisen. fileFilter corta antes de escribir nada si el tipo MIME no es una imagen conocida; limits.fileSize corta si pesa de más. Ambos casos se capturan en subirImagenConError y se muestran como mensaje-error en el propio formulario, en vez de tirar la app con un error 500.

Por qué la carpeta no está fija en el código

La primera versión guardaba en public/uploads/ a secas. El problema: en Railway el disco normal se borra en cada redeploy. La solución fue subir la responsabilidad un nivel — server.js resuelve la carpeta una sola vez a partir de UPLOADS_DIR y la deja colgada del objeto app, para que cualquier ruta la lea sin importar y sin repetir el cálculo:

server.js
const carpetaUploads = process.env.UPLOADS_DIR
  ? path.resolve(process.env.UPLOADS_DIR)
  : path.join(__dirname, "public", "uploads");
fs.mkdirSync(carpetaUploads, { recursive: true });
app.set("carpetaUploads", carpetaUploads);
app.use("/uploads", express.static(carpetaUploads));

En tu ordenador, sin configurar nada, sigue siendo public/uploads/. En Railway, UPLOADS_DIR=/app/data/uploads apunta dentro del volumen persistente — el mismo disco donde ya vive blog.db — así que sobrevive a los redespliegues igual que la base de datos.

09

Comentarios y moderación

Cualquiera puede comentar sin cuenta; solo el admin puede borrar. La moderación es deliberadamente simple: no hay estado "pendiente de aprobar", un comentario aparece al instante y el admin lo revisa después.

GET/admin/comentariostodos los comentarios, más recientes primero
POST/admin/comentarios/:id/borrarborra uno

El listado hace un JOIN con posts solo para poder mostrar el título del artículo junto a cada comentario, sin que el admin tenga que adivinar de qué post viene:

routes/admin.js
SELECT comentarios.*, posts.titulo AS post_titulo
FROM comentarios
JOIN posts ON comentarios.post_id = posts.id
ORDER BY comentarios.fecha_creacion DESC
10

SEO

routes/seo.js genera dos archivos que normalmente serían estáticos, pero aquí se calculan en cada petición para que la URL nunca esté mal escrita.

GET/robots.txtpermite todo salvo /admin, apunta al sitemap
GET/sitemap.xmluna URL por artículo, generada desde la tabla posts

Como el sitemap consulta la base de datos en cada petición en vez de ser un archivo fijo, un artículo nuevo aparece ahí automáticamente, sin acordarte de regenerar nada. El mismo urlBase que ya conoces de res.locals es el que arma cada <loc>.

Cada vista de artículo añade también un bloque <script type="application/ld+json"> (datos estructurados Article de schema.org) y las etiquetas Open Graph desde header.ejs, para que un enlace compartido en redes muestre título, resumen e imagen en vez de una URL pelada.

Variables de entorno

Todas se leen con process.env.NOMBRE || valorPorDefecto, así que la app arranca sin configurar nada — pero en producción quieres definir las tuyas.

VariablePara qué
DB_PATHruta de blog.db
UPLOADS_DIRcarpeta de imágenes subidas
ADMIN_EMAIL / ADMIN_PASSWORDcredenciales del único usuario
SESSION_SECRETfrase para firmar la cookie de sesión
PORTpuerto del servidor

En local, dotenv las carga desde tu archivo .env (que nunca se sube a git). En Railway no hay .env en absoluto — esas mismas variables se definen directamente en el dashboard de la plataforma, y Railway las inyecta en process.env antes de arrancar tu proceso.

Despliegue en Railway

Railway está conectado a github.com/gonzalordea/blog-web. Cada git push a main dispara un build y un redeploy automáticos — no hay un paso manual de "subir a producción".

El sistema de archivos de un contenedor de Railway se descarta en cada redeploy, salvo la ruta que hayas montado como volumen persistente — en este proyecto, /app/data. Por eso DB_PATH y UPLOADS_DIR apuntan los dos ahí dentro: es lo único que sobrevive de un deploy al siguiente.

14

Qué falta

De lo que ya se habló y todavía no se construyó:

  • Comentarios pendientes de aprobación, en vez de publicarse al instante.
  • Protección CSRF en los formularios del admin (ver sección 11).
  • Monetización: Google AdSense o enlaces de afiliado, una vez haya tráfico.
